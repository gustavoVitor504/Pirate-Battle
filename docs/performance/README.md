## Analysis

- **Frame rate.** The target of 60 FPS is met with margin: the display refreshes at 120 Hz and the game averages ~109 FPS over three minutes of continuous combat. The p95 frame time of 16.6 ms is itself at 60 FPS; only 1.8 % of frames exceeded 20 ms and 0.1 % exceeded 33 ms, with no long tasks. The first 10-second window is lower (~93 FPS) while textures upload, shaders compile and the first enemies arrive.
- **Simulation cost.** The fixed 60 Hz simulation (up to 9 enemies, a few projectiles and ~24 animated display objects) showed no long tasks at any point; GPU and CPU time per frame were not profiled separately, but the full-screen water and island tiles on an integrated GPU are the most likely main cost.
- **Memory.** Across 10 start → play → quit cycles, DOM nodes, JS event listeners and canvases return to exactly the same values after every match (0 canvases on the menu), so listeners, the ticker, the Pixi app and its WebGL canvas are all released.
- **Heap growth investigation.** Used JS heap rises ~0.15 MB per cycle. Comparing heap snapshots after cycles 2 and 8 shows where it goes (results.json → heapGrowthBreakdown): of +845 KB, **705 KB is V8 compiled code** (the JIT tiering up as more code paths run), 108 KB native and 60 KB strings, while application objects grew by only **16 KB** (~3 KB per match, promises and async state). There is no leak of game entities, textures or listeners; the growth is in V8 runtime code caches, which are expected to level off once the code paths are warm.
- **Mock worker restart (found here, fixed).** In an earlier run, ranking requests made right after a long match occasionally returned HTTP 404: the browser had restarted the MSW Service Worker, which forgot the page and let requests reach the static host. The app now detects responses without the mock marker header, re-activates the mock and repeats the request. In the final run this happened once and recovered automatically; the only trace is the browser console line for that first 404 (results.json → httpErrors).

## Limitations of these measurements

- One machine with an integrated GPU (Intel UHD, 120 Hz display); FPS is capped by the refresh rate, so 60 Hz displays will show ~60 FPS with more headroom per frame.
- Measured in a **visible** Chrome window at 1600×900, DPR 1. Headless Chrome does not pace frames to the display and is not representative; an occluded or minimized window is throttled and invalidates a run. On high-DPI screens the canvas resolution is capped at 2×.
- The scripted pilot is driven through Playwright (keyboard over CDP) and state is sampled once a second; both add a little overhead that a real player would not.
- The player is invulnerable so the full three minutes are measured with combat; sound is muted. GPU memory is not measured directly (only JS heap, DOM and listeners).
